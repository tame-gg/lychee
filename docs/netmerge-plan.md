# Lychee network merging: `lychee-netd`, net-merge's engine ported into Lychee (plan)

Date: 2026-10-19. Read against `~/work/s3/net-merge` at `227c4dd` (v0.3.1, MIT) and `~/work/s3/lychee` at `fb2ebd3` (v0.1.1, `main`), plus branch `s3/sidebar` at `8efd6bc` for the sidebar the Network page hangs off. Supersedes the 2026-10-17 revision (read against net-merge `2093cc1`, v0.3.0), which proposed shipping net-merge as a separate helper binary. Planning only; nothing outside `docs/` was changed. The control protocol is specified separately in `docs/netd-control-channel.md`.

Andrew's ask: "find a way to integrate this into lychee. same idea, but systemwide. this has it in the menu bar, i want it inside of a gui based thing. so it shows total combined speed, speed from each source just like now."

**Decision (Andrew, final).** net-merge is not a separate program, repository or download any more. Everything lives in `tame-gg/lychee` and ships as Lychee. net-merge's Go engine (MIT, credited) is ported into this repo under `native/netd/` as Lychee's own privileged service, `lychee-netd`, compiled by Lychee's own build (`npm run build:netd`) and packaged by electron-builder inside the Lychee installer. A small separate privileged process is still needed, and only because the operating system requires root or an administrator token (or `CAP_NET_ADMIN` on Linux) to create a TUN adapter and change routes; the Electron app itself never runs elevated. Lychee's main process starts `lychee-netd serve --control <path>`, talks to it over the local-socket JSON protocol in `docs/netd-control-channel.md`, owns elevation, crash handling and settings, and the renderer gets a "Network" page in the sidebar that reuses the existing throughput chart, combine diagram and network row components. Merging is off by default. A system-proxy fallback (option C, built on the engine's SOCKS5 code) stays a later option if demand appears; porting the engine to TypeScript (B) is not realistic; Lychee-only (D) is what exists today and stays the default mode.

Physics first, because it shapes every UI string: one TCP connection always rides one link. Neither net-merge's engine nor Lychee can make a single connection faster than the link it is on without MPTCP or an aggregation server. Combined speed comes from spreading many connections. Lychee already does that for its own downloads by opening streams bound to each adapter. System-wide merging extends the same trick to every other app (Steam, browsers, OS updates) by capturing their new connections and re-dialing each from one adapter.

## 1. What net-merge is, precisely (the engine being ported)

Paths in this section are net-merge's at `227c4dd`. In the port they sit under `native/netd/` with the same package names (section 9); `internal/tray`, `internal/icon` and `internal/state` are not ported.

### 1.1 How it combines links (`internal/tun`, `internal/engine`, `internal/nics`)

- **Capture.** `Tun.On()` in `internal/tun/tun.go` opens a virtual adapter through tun2socks' device layer (`tun.Open(openName, MTU)`), creates a gVisor netstack (`core.CreateStack`), then `configure()` (per OS: `tun_linux.go` via netlink, `tun_darwin.go` via `ifconfig`/`route`, `tun_windows.go` via `netsh`/`route.exe`) gives it `198.18.0.1/24` and the ULA `fd6e:6d65:7267::1/64` and adds two `/1` routes per family (`routes4 = 0.0.0.0/1, 128.0.0.0/1`, `routes6 = ::/1, 8000::/1`). Those beat any `/0` default without touching it, so `Off()` is just deleting them. Default MTU is 9000 (`DefaultMTU`), because TUN traffic never leaves the machine and bigger packets cut CPU about 3x. The adapter is named `net-merge` (`tunName`; macOS only accepts `utunN`) with a fixed Wintun GUID; the port renames it `lychee-netd` with its own GUID (section 9).
- **Terminate and re-dial.** Every TCP/UDP flow entering the TUN is terminated in gVisor and handed to `tunProxy.DialContext` / `DialUDP`, which call `Balancer.DialPinned` and `Balancer.ListenUDP` (`internal/engine/flowconn.go`, `balancer.go`). `DialTCP` builds a `net.Dialer` with `LocalAddr` set to the chosen adapter's IP **and** `Control: nics.ForceEgress(idx, v6)`. `ForceEgress` is what prevents a routing loop: `IP_UNICAST_IF` on Windows (`nics/egress_windows.go`), `SO_BINDTOIFINDEX` with `SO_BINDTODEVICE` fallback on Linux (`egress_linux.go`), `IP_BOUND_IF`/`IPV6_BOUND_IF` on macOS (`egress_darwin.go`). On macOS a bound socket only consults that interface's *scoped* routes, and the primary service has no scoped default, so `tun_darwin.go` keeps a scoped default route per real adapter in sync every 3 s (`startScopedSync`/`syncScoped`) while capture is on.
- **IPv6 at the SYN.** `internal/tun/forward.go` replaces tun2socks' forwarders so a refused IPv6 TCP flow gets a RST before the handshake completes (Happy Eyeballs then moves to IPv4) and refused UDP gets ICMP unreachable. The TUN's IPv6 address is a ULA on purpose so RFC 6724 source selection prefers IPv4 for dual-stack sites.
- **Pause without tearing down on macOS.** `keepDevice = true` in `tun_darwin.go`: `Off()` removes routes but keeps the utun, and `Warm()` creates it early, because creating or destroying a utun makes macOS drop a TetherKit (Android USB) link.
- **Adapter discovery** (`internal/nics/nics.go` `DiscoverNicsDetailed`): up, non-loopback interfaces, minus virtual ones by name/description regex (`virtualName` includes `tailscale|wintun|net-merge|docker|^wg\d|^tun\d|...`; the port adds `lychee-netd` and keeps `net-merge`), minus adapters the OS says are not hardware or have no default gateway (`info_linux.go` sysfs `device` link + netlink default routes in any table; `info_darwin.go` `^(en|feth)\d+$` + `DefaultRoutes()` from the routing socket, scoped ones included; `info_windows.go` `GetAdaptersAddresses` ifType whitelist + gateways). Re-scanned every 3 s (`-rescan`). Skips come back with reasons (`[]Skip`), which the control channel's `list_adapters` exposes.

### 1.2 Scheduler and weights (`internal/engine/sched.go`)

`Scheduler` is weighted least-active-flows, per address family. `AcquireFor(f, skip)` picks, among the best non-empty tier (0 = probed up, 1 = unprobed, 2 = probe failed or link-error cooldown), the slot with the lowest `(activeFlows+1)/weight`, starting from a random index so ties don't resonate with arrival patterns. `Tick(dt)` runs once a second: it reads OS byte counters for every adapter (section 1.5), computes per-family relayed rates, tracks a `peak` per family (decays 3%/s only while in use and underperforming; an idle adapter's estimate drifts back up toward half the best so it keeps getting re-measured), and with auto-weights on sets `weight = max(0.05, peak/maxPeak)`; weights stay equal until every adapter has carried `minMeasuredPeak` (50 KB/s). `-weight Name=3` fixes weights and disables auto for everyone (`SetAuto(c.auto && len(c.weights)==0)` in `cmd/net-merge/main.go`); there is no per-adapter manual override today, which the control channel's `set_weight` adds. Link-level dial errors (`classify()` in `balancer.go`: ENETUNREACH, EADDRNOTAVAIL, ...) sideline an adapter for `FailCooldown` 15 s and retry on another. `Snapshot()` returns `[]SlotStats` with `Name, IP, IP6, State, State6, Weight, Weight6, Present, Active, Total, Failed, BytesIn/Out, RateIn/RateOut` (relayed) and `LinkIn/LinkOut` (OS counters), `Peak/Peak6`.

### 1.3 Probes and captive portals (`internal/engine/probe.go`)

A TCP connect bound to the adapter (same `ForceEgress`) to `1.1.1.1:443` or `8.8.8.8:443` (v6: Cloudflare/Google anycast), 2 s timeout; every 15 s while up, every 4 s while down, immediately for a new adapter or changed address. Honest caveat: this is a TCP handshake, not an HTTP 204 check. A captive portal that answers the SYN and hijacks the TLS/HTTP layer passes this probe, so a hotel Wi-Fi can still receive flows that then fail. Portals that drop unauthenticated traffic at the firewall are caught correctly.

### 1.4 IPv6 policy and autopause

`Balancer.V6Mode` is `auto|on|off` (`balancer.go`). `auto` (the tray checkbox "Use all adapters") only balances IPv6 when `Scheduler.V6CoversAll()` says every adapter that carries IPv4 also carries working IPv6; otherwise IPv6 is refused so apps fall back to IPv4 and every adapter stays in use, at the cost of IPv6-only hosts. Autopause lives in `internal/tray/autopause.go` as a pure state machine (`autoPauser.tick(now, on, usable, active)`): pause after 10 s idle with fewer than two usable connections (2 min if data is still moving, `quietRate` 50 KB/s), resume 3 s after two connections work, never more than one automatic switch per 30 s, and a manual pause is never undone (`userSet`, `manualOff`). It is thoroughly tested (`autopause_test.go`) but packaged under `tray`; the port moves it, unchanged and with its test, to `internal/control`.

### 1.5 Per-interface speed (`internal/nics/counters_*.go`)

`Octets(idx)` reads the kernel's byte counters for an adapter: Linux `/sys/class/net/<name>/statistics/rx_bytes|tx_bytes`; macOS `syscall.RouteRIB(NET_RT_IFLIST2)` parsing `if_msghdr2` (64-bit `ibytes`/`obytes` at offsets 96/104); Windows `GetIfEntry2Ex` `InOctets/OutOctets`. `Scheduler.Tick` samples them every second into `linkRateIn/Out` with a counter-reset guard. These count **every app's traffic** on the adapter, which is exactly the "total combined speed" Andrew wants and is why the tray shows real speeds even while paused. They also include Lychee's own streams (see section 7 on double counting).

### 1.6 Tray UI contents (`internal/tray/tray.go`, not ported)

Header: `Merging · Total ↓X ↑Y Mbps` / `Paused` / `Paused: one connection` / `Error: …`. Up to `trayRows = 4` adapter rows: `name: ↓X ↑Y Mbps (N flows via net-merge) - <state> +IPv6`. Checkboxes "Use all adapters (IPv6 only if every adapter has it)" and "Pause when there is only one connection", a "Start merging"/"Pause merging" item, "Quit". Hover tooltip trimmed to 63 UTF-16 units for Windows (`trayTooltip`). Green/grey icon drawn in `internal/icon`. Refresh once a second. Everything the GUI page needs is in `SlotStats` plus the autopause word, which is why the tray, the icon and `fyne.io/systray` are not ported: the Network page (section 6) is the UI.

### 1.7 CLI/IPC surface: files, not sockets (`internal/state/state.go`, not ported)

`net-merge on|off|quit|status` talk to the running tray through a per-user directory (`DefaultDir()`: `%LOCALAPPDATA%\net-merge` on Windows, `~/.cache/net-merge` on Linux, fixed root-owned `/var/run/net-merge` on macOS). While ON, `boot()` writes `status.json` once a second (`Status{PID, Mode, V6, Since, Updated, NICs []SlotStats}`); `Read` treats it as live only if `Updated` is under 3 s old; `Clear` removes it on OFF. Commands are empty marker files in a sticky world-writable `ctl/` (`SendMarker`/`TakeMarker` for `on`, `off`, `quit`), polled every second by the tray loop and every 300 ms by `run`. Single-instance detection (`internal/platform/platform_*.go`): a `Global\net-merge` mutex, a Linux abstract unix socket `@net-merge`, or a flock on `/var/run/net-merge.lock`. Consequences: there is no status while paused, no runtime toggles for IPv6/autopause/include/weights, no "why did it fail" channel, and no auth beyond directory permissions. **None of this is ported.** `lychee-netd` has one control path, the JSON channel of `docs/netd-control-channel.md`, and its own lock names; it only *looks* for net-merge's lock names so that a standalone net-merge and `lychee-netd` never run together (section 7).

### 1.8 Privileges per OS (`internal/platform`)

Windows: `IsAdmin()` is the elevated token; `RelaunchElevated` is `ShellExecute runas`; `CheckDriver` requires `wintun.dll` next to the exe; autostart is a scheduled task with `RunLevel HighestAvailable` so sign-in start needs no UAC (`autostart_windows.go`). macOS: root (`Geteuid()==0`); GUI elevation via `osascript "do shell script … with administrator privileges"`; `sudo net-merge install` copies the binary root-owned to `/usr/local/bin/net-merge` (refusing if any parent dir is writable by non-root, `copyRootOwned`) and writes `/etc/sudoers.d/net-merge` allowing exactly `net-merge tray` and `net-merge cleanup` without a password, validated with `visudo -cf` (`install_darwin.go`); `RelaunchTray` uses `sudo -n` when that rule exists. Linux: `IsAdmin()` reads `CapEff` for `CAP_NET_ADMIN`; packages run `setcap cap_net_admin,cap_net_raw+ep` in `packaging/postinstall.sh`; the tray refuses to run as root because the StatusNotifierItem lives in the user's D-Bus session (`RelaunchTray` in `platform_linux.go`); `run` elevates with `sudo` or `pkexec`. The port keeps `IsAdmin`, `CheckDriver`, `SingleInstance`/`InstanceRunning`, the `copyRootOwned`/`rootOnly` helpers and the task XML, under Lychee's names (section 4); the relaunch and tray helpers go.

### 1.9 Crash safety

The TUN is a file descriptor: when the process dies the kernel removes the adapter and every route on it (Linux TUN, macOS utun, Wintun). `scripts/linux-e2e.sh` and `scripts/macos-smoke.sh` verify `kill -9` leaves the machine with internet. What survives a crash: macOS scoped default routes (`cleanupScoped` removes them on the next start and `net-merge cleanup` does it by hand) and, on Windows, possibly routes on a surviving adapter (`CleanupStale`). `cmdTray` also closes the TUN on SIGINT/SIGTERM. The Inno installer kills a running instance before replacing files precisely because this is safe.

## 2. Lychee architecture relevant to this

- **Stack.** Electron 44 + React 19 + TypeScript, electron-vite, Zustand store, Tailwind v4, Base UI (`package.json`, `electron.vite.config.ts`). Main is bundled as CommonJS. `koffi` is the FFI used on Linux (`SO_BINDTODEVICE`) and Windows (`download/sparseFile.ts`); `electron-builder.yml` only ships koffi prebuilds for `linux_x64|linux_arm64|win32_x64|win32_arm64`.
- **How downloads bind to interfaces.** `src/main/network/routes.ts`: `StreamConnection` owns keep-alive HTTP/HTTPS agents whose `createConnection` is `connectOnInterface()`, a Happy-Eyeballs race over `routesFor(iface, resolvedAddresses)`; each candidate socket comes from `connectRoute()` in `deviceBinding.ts`. On Linux that opens a raw libc socket, sets `SO_BINDTODEVICE`, and hands the fd to Node (`deviceBindingSupported()` probes kernel ≥ 5.7, else falls back). On macOS and Windows it is a plain `net.connect({ localAddress })`, trusting the OS to route by source address. Torrents go through the same `connectRoute` via a patched webtorrent `connect` hook (`torrent/torrentTransfer.ts connect()`, `patches/webtorrent+3.0.21.patch`), with uTP/WebRTC/web seeds disabled (`torrent/engine.ts`).
- **How per-network speed is measured.** Per download: `Meters` in `download/transfer.ts` count bytes as they arrive (`HttpTransfer.onNetworkProgress`, `wire.on('piece')`) and are read on the 500 ms tick in `DownloadManager.run` (`updateSpeeds`, 3 s window). Once a second `sampleSpeeds` appends to `state.speedHistory` (60 samples, `SPEED_HISTORY_SECONDS`). Nothing reads OS counters; Lychee only knows its own bytes.
- **Existing network UI.** `NetworksMenu.tsx` (header popover): every interface with name, OS name badge, limits, and the summed speed of running downloads on it plus a total in the trigger. `NetworkRow.tsx` (per-download table with streams/peers expansion). `ThroughputChart.tsx` (stacked area per network over 60 s, hover readout, `speedTicks`). `CombineDiagram.tsx` (links converging into one stream). `NetworkEditPopover.tsx` (rename/recolor, persisted in `networkPreferences`). `useNetworkVisuals` assigns colors by interface id across the whole app. `DownloadsSidebar.tsx` (branch `s3/sidebar`, not merged yet) with Status and File type sections; `useAppStore.view` is `{name:'list'} | {name:'download', id}`.
- **Interface list.** `src/main/network/interfaces.ts` `listActiveInterfaces()`: `os.networkInterfaces()` minus internal/link-local, labels from `networksetup -listallhardwareports` (macOS) and `Get-NetAdapter` (Windows), kind from names/descriptions. It does **not** filter VPNs or virtual adapters (Tailscale's utun with 100.x shows up as "other"), and the id is the OS device name. `NetworkMonitor` polls every second and pushes `IpcChannels.networksChanged`.
- **Settings and IPC.** `settings.ts` whitelists fields in `app-settings.json` (`sanitizeSettings`); `InitialState` is read synchronously in `preload/index.ts`; typed channels in `shared/ipc-channels.ts` and `shared/ipc-contract.ts`, handlers in `ipc/handlers.ts`, store persistence via `persist()` in `useAppStore.ts`. e2e tests (`e2e/fixtures.ts`) drive `window.lychee` and use env knobs from `testKnobs.ts` (`LYCHEE_E2E_INTERFACES` fakes the interface list).
- **Platforms, packaging, updater.** Windows x64+arm64 in one NSIS assisted installer (`nsis.oneClick: false`, `build/installer.nsh`); macOS dmg+zip per arch, ad-hoc signed by default (`identity: '-'`, `hardenedRuntime: false`), Developer ID + notarization when secrets exist (`.github/workflows/release.yml`); Linux AppImage/deb/rpm x64+arm64. `asarUnpack: resources/**`, `afterPack: scripts/check-torrent-package.mjs` (a precedent for packaging assertions; electron-builder takes one `afterPack` hook, so a second check means a small dispatcher). Updates via `electron-updater` generic provider `https://cdn.tame.gg/lychee/` (`updater.ts`): installable on Windows always, macOS only with Developer ID, Linux only AppImage. There is no `NOTICE` file on `main` yet; S1's branch `s1/netmerge-notice` (PR #11) adds one (section 12).
- **Lifecycle.** `main/index.ts`: `before-quit` calls `downloadManager.suspendAll()` with a 3 s force-exit; `window-all-closed` quits on Windows/Linux unless the browser extension was used, in which case Lychee stays in an Electron `Tray` (`keepsRunningForBrowser()`). The README states Lychee "needs no virtual adapter, VPN, kernel extension, or administrator rights", which this feature changes for an opt-in mode.

## 3. Integration options

### A. `lychee-netd`: net-merge's engine ported into Lychee (decided)

The Go engine (`internal/engine`, `internal/nics`, `internal/tun`, `internal/platform`, `internal/logx`, plus `autoPauser`) is copied into this repository at `native/netd/` as module `github.com/tame-gg/lychee/native/netd`, with `native/netd/UPSTREAM.md` recording that it was ported from net-merge `227c4dd` (v0.3.1) and `native/netd/LICENSE-net-merge` keeping the MIT text. It becomes one binary, `lychee-netd` (`lychee-netd.exe` on Windows), with exactly two subcommands: `lychee-netd serve --control <path>` runs the engine headless behind the control channel, and `lychee-netd version` prints the version baked in at build time (Lychee's `package.json` version). There is no tray, no icon, no CLI on/off/status, no file protocol, no `install`/`autostart` subcommand: `internal/tray`, `internal/icon`, `internal/state` and the `fyne.io/systray` dependency are not ported, and the SOCKS5 front end (`engine.ServeSocks5`) stays in the package as code but is not exposed. Lychee's own build compiles it (section 10), electron-builder packages it under `resources/helper/` (section 11), Lychee's main process launches it with the OS's privilege mechanism (section 4), and the renderer shows its status (section 6).

Why a separate process at all: creating a TUN adapter and adding routes requires root on macOS, root or `CAP_NET_ADMIN` on Linux and an elevated token on Windows, and the Electron app must never run that way (Chromium refuses to run as root on Linux without disabling its sandbox, and an elevated renderer would put every web page behind an admin token). So the privilege boundary is the control channel: a small Go process with the privilege, an unprivileged app that tells it what to do, peer credentials deciding who may talk. Everything that makes net-merge work (TUN, gVisor, egress pinning, probes, weights, autopause, crash safety) is reused as is; the engine code the port touches is listed in section 9.

There is no longer a "phase 0" that drives a stock net-merge binary through its file protocol: that protocol is not ported, so the first runnable piece is L-1's `serve`, exercised by its Go tests and by a tiny command-line client, and the UI is developed against the fake netd of L-3 before the real binary is wired in. In-repo port, not a fork: upstream fixes are carried over by hand against the commit recorded in `UPSTREAM.md`.

Pros: battle-tested engine, every app and protocol covered (TCP, UDP, v4, v6), crash-safe by construction, CPU ~0.18 cores per 100 Mbit/s, one repository, one version number, one installer. Cons: admin/root/capabilities; a driver on Windows; a Go toolchain in Lychee's build; signing and notarization of a Go binary; Windows arm64 deferred (section 4).

### B. Port the engine to TypeScript/Node (not feasible)

Opening the device is the easy part (koffi could `open("/dev/net/tun")`, do the macOS `PF_SYSTEM`/utun dance, or load `wintun.dll`). The hard part is the userland TCP/IP stack: gVisor netstack implements TCP (congestion control, SACK, retransmission, window management) and a UDP NAT, and there is no production-quality JavaScript equivalent. Even if one existed, pushing hundreds of Mbit/s of 9000-byte packets through the Electron main process's single event loop would starve the download engine that lives in the same process. And the whole Electron app would have to run as root/admin, which is unacceptable (see A). A worker-thread or child Node process does not change the stack problem. Rejected.

### C. System proxy mode (possible later, lower privilege)

The engine has a SOCKS5 front end (`engine.ServeSocks5`, CONNECT only, no UDP ASSOCIATE, no admin). Lychee would set the OS proxy to `socks5://127.0.0.1:1080` and revert it later: Windows per-user WinINET registry (`ProxyEnable`/`ProxyServer`/`ProxyOverride`) plus `InternetSetOption` refresh; macOS `networksetup -setsocksfirewallproxy <service>` per service (needs admin anyway on modern macOS); Linux `gsettings org.gnome.system.proxy` / KDE `kioslaverc` / env vars. Honest limits: only apps that honor the system proxy (browsers yes; many games, launchers, updaters, CLI tools no); no UDP, so QUIC falls back to TCP and DNS stays on the default route; many Windows apps want an HTTP proxy, so we would add an HTTP CONNECT front end on the Go side (~150 lines); a bypass list for LAN/private ranges is mandatory. Crash safety is worse than TUN: a stale proxy setting makes every proxy-aware app offline until reverted (section 5). Worth building only as "browser-only mode" for users who cannot elevate, or if a platform's elevation story proves untenable. Not scheduled (section 13, "mode C later if wanted").

### D. Lychee-only (status quo)

Per-download multi-stream, per-network binding, per-network limits and charts for Lychee's own transfers. No admin. It does not meet "systemwide", but it remains the default and the Network page must show these numbers too (as "Lychee" rows) when netd is off.

**Decision: A, decided; D stays the default mode; C only if real demand appears.**

## 4. Privileges, installers and the updater

Common to all platforms: the packaged binary lives at `process.resourcesPath/helper/lychee-netd[.exe]` (electron-builder `extraResources`, section 11). Lychee starts it as `lychee-netd serve --control <path>` and checks the `hello` handshake's `helper_version` against its own `app.getVersion()`; both are the `package.json` version, so anything else is "Network helper is out of date" with a repair action (which re-runs the per-OS install step). Where the OS needs a root-owned copy outside the app (macOS, Windows), `lychee-netd version` on that copy is the cheap pre-launch check. The Windows arm64 build ships without netd (amd64 only for now); on it the Network page shows "Unsupported here".

**Windows (NSIS; netd for x64 only, arm64 deferred).** Wintun adapter creation and `route add` need an elevated process. Three ways, in order of preference: (1) first enable triggers one UAC prompt (`ShellExecute runas`) that runs an elevated copy step; afterwards a scheduled task with `RunLevel HighestAvailable` (net-merge's `autostart_windows.go` task XML, pointed at the new path) starts the elevated helper without a prompt via `schtasks /Run`. (2) UAC every time merging is turned on; simplest, annoying. (3) A Windows service installed by the installer; not viable because Lychee's assisted installer can be per-user and the auto-updater runs unelevated. Elevated children cannot inherit stdio pipes from an unelevated parent, so the control channel is a named pipe `\\.\pipe\lychee-netd-<user SID>` created by the helper (rules below).

**Windows helper install location.** The NSIS installer is per-user by default and installs under `%LOCALAPPDATA%`, which the user (and any program the user runs) can write to. The elevated scheduled task must never run the helper from there, or replacing `lychee-netd.exe` would give admin at the next sign-in. When merging is first enabled, one UAC prompt runs an elevated copy step that places `lychee-netd.exe` and the unmodified `wintun.dll` (plus `wintun-LICENSE.txt`) in `%ProgramFiles%\Lychee\helper`. Before registering or starting the task, Lychee verifies that only SYSTEM and Administrators can write to that folder and its files (anything else, including inherited user write access, makes Lychee refuse to enable merging) and verifies the helper's Authenticode signature, or its SHA-256 against the hash embedded in the Lychee build while builds are unsigned. The scheduled task's action points only at `%ProgramFiles%\Lychee\helper\lychee-netd.exe serve --control \\.\pipe\lychee-netd-<SID>`. Lychee updates never write there directly: a new helper version is installed through the same elevated copy step with the same version and hash checks. `wintun.dll` stays the unmodified, WireGuard LLC-signed DLL, used only through `wintun.h`, as its Prebuilt Binaries License requires. The helper must be stopped before an update replaces files (file locks): `before-quit` sends `quit`, waits ≤ 1 s, kills if needed; the TUN dies with it either way.

**Windows named pipe.** The helper creates `\\.\pipe\lychee-netd-<SID>` with a protected DACL that grants only the logged-in user's SID (`GENERIC_READ | GENERIC_WRITE`) and SYSTEM (`GENERIC_ALL`): no Everyone, Authenticated Users or Administrators ACE (SDDL `O:<SID>D:P(A;;GRGW;;;<SID>)(A;;GA;;;SY)`), `PIPE_REJECT_REMOTE_CLIENTS`, and `FILE_FLAG_FIRST_PIPE_INSTANCE` so it fails instead of joining a pipe someone else squatted on first. For every connection the helper calls `GetNamedPipeClientProcessId`, opens that process's token and checks that the token's user SID equals its own; mismatches are disconnected. The client verifies the server's process SID before sending a byte (spec section 2.4).

**Windows needs an administrator account (S2).** UAC elevation keeps the same user only when that user is an administrator (the *consent* prompt). On a standard account the *credential* prompt elevates as whichever administrator typed their password, so the helper's token user, pipe name and DACL belong to that administrator and Lychee, running as the standard user, cannot connect. That fails safe (nobody else can control the helper, the client cannot connect, and nothing is captured because merging is off until an `on` request arrives and off by default anyway), but it is a dead end, so Lychee MUST detect it before launching (the current user is not a member of Administrators per the linked token / `CheckTokenMembership`) and after launching (the helper exits 6, or runs but the pipe cannot be opened or reports another SID) and show "Combining connections system-wide needs an administrator account on this PC", never "helper unavailable". Likewise the scheduled task with `RunLevel HighestAvailable` gives a standard user a limited (non-elevated) token that cannot create the Wintun adapter or routes: `lychee-netd serve` checks at start that its token is elevated and in Administrators and otherwise exits with the dedicated code 6 (`needs_admin`, spec section 2.7), which the client maps to the same message. Unsigned helpers mean a yellow "Unknown publisher" UAC and SmartScreen; code signing (which Lychee lacks too) is the real fix. Verify electron-builder signs exes under `resources/` when a certificate is configured; if not, add a sign step.

**macOS (dmg, per arch).** Root is required for the utun and routes. Options: (1) `osascript … with administrator privileges` each time merging is enabled; one password per Lychee session if the helper stays running and pause only drops routes (which it does, `keepDevice`). (2) net-merge's `install` pattern, decided: a one-time admin prompt copies the helper root-owned (`copyRootOwned` semantics: temp file, `chown 0:0`, mode `0755`, rename, refused if any parent directory is writable by non-root) to `/Library/PrivilegedHelperTools/gg.tame.lychee.netd` (`root:wheel`, `0755`) and writes `/etc/sudoers.d/lychee-netd` (`0440`, validated with `visudo -cf` on a temporary file before it is moved into place) containing exactly this:

```
# Written by Lychee: <user> may start the network helper without a password.
<user> ALL=(root) NOPASSWD: /Library/PrivilegedHelperTools/gg.tame.lychee.netd serve --control /var/run/lychee-netd/netd.sock
```

   No wildcards, no trailing `*`, no `""` empty-argument variant: sudo compares the command line exactly, so any other subcommand, flag or path is refused. Lychee's launch MUST be exactly `sudo -n /Library/PrivilegedHelperTools/gg.tame.lychee.netd serve --control /var/run/lychee-netd/netd.sock`. Lychee re-reads and byte-compares the installed file before relying on it: the elevated setup step reads it back right after the rename and compares it with the expected content (with `<user>` substituted), mode and owner, failing the setup on any difference (the file is unreadable to the GUI user, so the comparison lives there), and before every launch the unprivileged client runs `sudo -n -l` with the exact command line, which succeeds only if sudo accepts it (spec section 3.3). `/Applications/Lychee.app` is typically user-owned, so the copy must leave the bundle, and Lychee updates do not update the root-owned copy: Lychee compares `lychee-netd version` of the installed copy (and `helper_version` from `hello`) with its own version and offers "Update network helper" (one admin prompt, same install step). (3) The Apple way: `SMAppService`/`SMJobBless` privileged LaunchDaemon with `SMPrivilegedExecutables`/`SMAuthorizedClients` pairing. It requires the app and helper to be signed with the same Developer ID, which the ad-hoc default build is not, and a native shim to call the API from Electron. (2) now, (3) once signing lands. Peer auth: the rule allows no other arguments, so the helper authenticates clients by `LOCAL_PEERCRED` uid equal to `SUDO_UID`; the socket is `/var/run/lychee-netd/netd.sock` (`0600`, chowned to `SUDO_UID`) in root-owned `/var/run/lychee-netd` (`root:wheel`, `0755`). Hardened runtime and notarization: list the helper under `mac.binaries` in `electron-builder.yml` so osx-sign signs it; Go binaries are fine under hardened runtime, and the helper needs no cgo (section 10).

**Linux (AppImage, deb, rpm).** The helper needs `CAP_NET_ADMIN` (and `CAP_NET_RAW` before kernel 5.7). deb/rpm install it root-owned at `/usr/lib/lychee/lychee-netd` and run `setcap cap_net_admin,cap_net_raw+ep /usr/lib/lychee/lychee-netd` in `afterInstall` (mirrors net-merge's `packaging/postinstall.sh`; file capabilities are dropped when the file is replaced, so the script runs on every upgrade). With capabilities the helper runs as the user and the control socket is `$XDG_RUNTIME_DIR/lychee/netd.sock` (directory `0700`). AppImage: the squashfs is mounted `nosuid`, so file capabilities are ignored; Lychee runs `pkexec <abs path> serve --control /run/lychee-netd/netd.sock` (polkit GUI prompt) once per Lychee session; the helper then runs as root, uses `/run/lychee-netd` (root-owned, `0755`) with the socket `0600` chowned to `PKEXEC_UID`/`SUDO_UID`, and checks `SO_PEERCRED` against that uid. This pkexec path runs a binary from a user-writable folder (the AppImage mount or its extraction dir); that is accepted because pkexec requires the admin password on every start, so a swapped binary gains nothing without the user typing the password. `/dev/net/tun` must exist (`CheckDriver`). Firewalls: trust the `lychee-netd` interface in firewalld/ufw, as net-merge's README and `nix/module.nix` do for `net-merge`. Electron's own `Tray` already handles StatusNotifierItem, so none of net-merge's tray code is needed.

**Updater interactions.** Helper path is stable across updates on all three OSes. Windows: stop the helper before `quitAndInstall`; the admin-only copy in `%ProgramFiles%\Lychee\helper` is replaced only through the elevated copy step with version and hash checks. macOS: the root-owned copy has its own update prompt. Linux deb/rpm: `afterInstall` re-applies caps; AppImage: nothing to do. Always: `version` handshake, and refuse to turn merging on with a mismatched helper.

## 5. Crash safety and revert

**TUN mode.** Nothing to revert by design: adapter and routes vanish with the process (verified by net-merge's e2e scripts, which move into `native/netd/scripts/`). Lychee adds: (a) on every helper start the engine already calls `CleanupStale()` (stale routes, macOS scoped defaults, Windows weak-host settings); (b) a watchdog in `MergeController`: if the control connection drops without a `quit` ack, state becomes "Helper stopped unexpectedly" with a Restart action and the last 60 s of history kept; (c) a "Repair network" action that sends `cleanup` over the channel (allowed only while off) for the macOS scoped-route residue; (d) the helper writes no log file itself: Lychee captures its stderr (where the launch mechanism passes it through) and the channel's `log` events into `userData/logs/lychee-netd.log`, and an "Export diagnostics" bundles that log with the helper's adapter list and skip reasons (`list_adapters`).

**Proxy mode (if built).** The proxy setting outlives both processes, so: a revert journal in `userData/proxy-revert.json` written *before* changing anything (previous values per Windows user / per macOS service / per gsettings key); restore on Lychee startup if the journal exists and no helper is running; a detached guardian process that waits for Lychee's PID to exit and restores from the journal; a visible "Turn off and restore proxy" panic button; and never set a proxy without a bypass list. Document that a hard power cut can still leave the setting until Lychee next runs.

## 7. Coexistence with the download engine

**Do Lychee's bound sockets bypass the TUN?** Linux: yes on kernels ≥ 5.7, because `SO_BINDTODEVICE` restricts route lookup to that device (this is the same mechanism the engine relies on). On older kernels Lychee falls back to `localAddress` only (`deviceBindingSupported()` false, `NetworkBindingDialog`), and those streams would be captured and re-balanced by the helper; acceptable, but the UI should say so. macOS and Windows: **unverified, and the single most important thing to test on Andrew's machines before anything ships.** Lychee binds only `localAddress`. The engine's own code says a socket bound to an adapter does a scoped lookup on macOS and falls through to the unscoped table (where the /1 routes live) unless a scoped default exists, which is why it maintains scoped defaults while ON; whether an implicitly bound socket (no `IP_BOUND_IF`) gets the same treatment is the open question. Windows' strong-host send model should constrain the lookup to the source interface, but the engine still sets `IP_UNICAST_IF` "even if the TUN's routes match". Plan: add `IP_BOUND_IF` (macOS) and `IP_UNICAST_IF` (Windows) to `connectRoute()` via koffi, mirroring `nics/egress_darwin.go` and `egress_windows.go` (koffi prebuilds for darwin must then be shipped too), and verify with the helper ON that each Lychee stream's source IP is the adapter's own and that `active_flows` in the helper do not jump when Lychee downloads. If pinning fails, Lychee's per-network attribution and limits are meaningless while merging, so this gates the feature; it is L-4, early in the stack.

**Hide the TUN from Lychee.** The helper's adapter (`lychee-netd` on Linux/Windows, `utunN` on macOS, address `198.18.0.1`; the channel reports it as `tun.name`) appears in `os.networkInterfaces()` and would be offered as a download network in `NetworksMenu`/`NewDownloadDialog`. Filter it in `listActiveInterfaces()` by the reported adapter name and by the `198.18.0.0/24` and `fd6e:6d65:7267::/64` prefixes (L-5).

**Double counting.** OS counters include Lychee's own bytes. The Network page shows OS totals (that is the point: everything on the machine). Each row can add a quiet "Lychee X of Y" using the per-network sum `NetworksMenu` already computes; the download screens and `NetworksMenu` keep showing Lychee-only speeds and get a "Lychee" label so the two totals are not confused. Never add the helper's `relayed_in_bps` to Lychee's meters: Lychee's streams are not relayed.

**Per-network limits and data caps.** `Limits.take()` meters only Lychee's bytes, so a phone hotspot's data limit in Lychee says nothing about Steam using it through the helper. Offer "Exclude from merging when its data limit is reached" (hook `limitReached` → `exclude`) and state the caveat on the Network page and in Speed & data limits.

**Torrents.** Peer connections are pinned via `connectRoute` (same verification as above). Incoming peers arrive on each adapter's own address and are untouched. The DHT and tracker sockets are unbound, so they enter the TUN while merging; each is one UDP socket, so it is pinned to one adapter for its life (`udpSessionTimeout` 30 s idle) and keeps working. Lychee's `probeUrl`, DNS (`dns.lookup`), updater and bridge are unbound too; they are balanced like any other app's traffic, which is fine.

**A standalone net-merge on the same machine.** Both tools would install the same `/1` routes, so they must never run together. `lychee-netd` takes its own single-instance lock (`@lychee-netd` abstract socket on Linux, `/var/run/lychee-netd.lock` on macOS, `Global\lychee-netd` on Windows) and additionally probes net-merge's lock names (`@net-merge`, `/var/run/net-merge.lock`, `Global\net-merge`); if either is held it exits 4 with "another connection-merging tool is running", which the Network page shows verbatim. The adapter names (`lychee-netd` vs `net-merge`) and Wintun GUIDs differ, so the adapters themselves never collide. A net-merge started *after* `lychee-netd` does not know Lychee's lock and fails at its own `route add` (or, on Windows, the last route added wins); the user removes one of the two tools.

**Lifecycle.** If merging is on and the window closes on Windows/Linux, today the app quits (`window-all-closed`) and merging would stop. Reuse the existing tray path (`keepsRunningForBrowser`) with the "keep merging in the tray" setting, and show merging state in the tray menu. On quit, `before-quit` must stop the helper inside the existing 3 s budget; the helper also stops by itself 10 s after its client disconnects (spec section 10.3), so a crashed Lychee never leaves it running.

## 8. Risks

- **VPNs, Tailscale in particular (installed on these machines).** The helper skips `tailscale0`/utun by name and lack of hardware, and Tailscale's own routes (100.64/10, per-peer /32) are more specific than /1, so normal Tailscale use is unaffected. Exit-node mode is the conflict: on Linux Tailscale uses policy routing (table 52) that wins over the main table, so merging silently does nothing; on macOS/Windows Tailscale installs its own `0/1` and `128/1` routes, colliding with the helper's (one `route add` fails, or whoever adds last wins). Detect `tailscale status --json` exit-node state or existing /1 routes before enabling and refuse with a clear message. MagicDNS (100.100.100.100) is unaffected.
- **Captive portals** pass the TCP-only probe (1.3). Add an HTTP 204 probe in `internal/engine/probe.go` later; let users exclude an adapter.
- **DNS.** Queries to on-link resolvers (router, hotspot gateway) are not captured; queries to public resolvers are balanced and may leave via either ISP. Each ISP sees part of the DNS and traffic; that is inherent to merging and belongs in the feature's disclosure text.
- **Sites tying sessions to IP.** Each connection may exit from a different public IP, so some logins and CAPTCHAs break (documented by net-merge). A per-destination affinity would help but reduces balance; engine idea, not in scope.
- **IPv6-only hosts** unreachable in `auto` when adapters differ; the toggle exists and must be explained.
- **Hotspot data caps and battery.** Merging sends every app's traffic over the phone: Windows Update, cloud sync, Steam. Make the warning conspicuous, default autopause on, and provide one-click exclusion.
- **macOS TetherKit drop** on utun create/destroy: handled by the engine's `keepDevice`/`Warm()`, but the helper must start before the Android phone is connected; show the hint.
- **Firewalls and antivirus.** Windows classifies the adapter as an unidentified (public) network; the fixed Wintun GUID keeps one profile. Unsigned Go binaries creating TUN adapters are a classic false-positive; sign both executables, never pack with UPX.
- **Enterprise policies.** No admin, MDM-managed Macs, AppLocker, standard Windows accounts: degrade to "Needs permission" / "Needs an administrator account" / "Unsupported here" and offer mode C or nothing.
- **Apps ignoring the proxy** only matter for mode C.
- **A standalone net-merge install.** Detected through its lock names; `lychee-netd` refuses to start (exit 4) and the page says so (section 7).
- **Positioning and support.** Lychee's README promise of no admin and no virtual adapter becomes "optional system-wide mode needs admin"; expect "my internet broke" tickets even though a crash cannot leave the machine offline. Diagnostics export and "Repair network" are the mitigation.
- **Latency and CPU.** All traffic traverses userland; a few hundred microseconds and ~0.18 cores per 100 Mbit/s. Gaming/VoIP users should be told.
- **Toolchain.** Every Lychee build now needs Go; a Go security release means a Lychee release. `go.mod`'s `toolchain` line pins the exact version (section 10).

## 10. Build

- **Toolchain.** `native/netd/go.mod` says `go 1.27` (as upstream) and adds a `toolchain go1.27.x` line pinning the exact release; Go's toolchain switching then downloads that version for a developer with a newer or older `go` on PATH. Developers need Go installed to run `npm run build:netd`, `test:netd` or any `build:*` script; `CONTRIBUTING.md` gets a "Requires Go 1.27+" line next to the Node requirement and a note that the engine tests on macOS need the loopback aliases net-merge's CI adds (`sudo ifconfig lo0 alias 127.0.0.2/32` and `.3`). If the release workflow is ever used for a build that contains netd, it needs one `actions/setup-go` step with `go-version-file: native/netd/go.mod`.
- **`scripts/build-netd.mjs`.** Runs, with `cwd` = `native/netd` and `CGO_ENABLED=0`, `go build -trimpath -ldflags "-s -w -X main.version=<package.json version>" -o ../../build/netd/<os>-<arch>/lychee-netd[.exe] ./cmd/lychee-netd` for each target: `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`, `windows/amd64`. Output directories use electron-builder's vocabulary so the `${os}-${arch}` macro resolves directly: `linux-x64`, `linux-arm64`, `mac-x64`, `mac-arm64`, `win-x64` (the script maps GOOS/GOARCH to these). A `--target` flag limits the list for local work; by default all five are built, since cross-compiling without cgo is cheap. For `win-x64` the script also calls `fetch-wintun.mjs` (section 11) unless `wintun.dll` with the pinned hash is already there. It writes `build/netd/win-arm64/UNSUPPORTED` (no binary) so the arm64 Windows package has a well-defined, empty `helper/` and Lychee shows "Unsupported here".
- **npm scripts.** `build:netd` (the script above), `test:netd` (`go vet ./... && go test ./...` in `native/netd`), and `build:netd` is prepended to `build:win`, `build:mac`, `build:linux` and `build:unpack`. `netd-notices.mjs` runs as part of `build:netd` so the notices file is always as fresh as the binary.
- **No cgo, verified.** net-merge's own code has no `import "C"`; the only cgo user in its dependency set is `fyne.io/systray`'s darwin backend, which is not ported (net-merge's release workflow builds macOS with `CGO_ENABLED=1` for exactly that reason). Checked on 2026-10-19 with Go 1.27.2 against the upstream module cache, offline: `internal/engine`, `internal/tun`, `internal/nics`, `internal/platform` and `internal/logx` compile with `CGO_ENABLED=0` for all five targets, and the full `cmd/net-merge` fails only inside `fyne.io/systray` on darwin. **Check item for L-1:** `build:netd` must pass on a Linux host for every target with `CGO_ENABLED=0`, and `go version -m build/netd/mac-arm64/lychee-netd` must show `CGO_ENABLED=0` and no `fyne.io/systray` module.
- **Windows binary flags.** Console subsystem (no `-H windowsgui`): the task scheduler and `runas` start it without a visible console in practice, and a console build keeps `lychee-netd version` usable from a shell; verify in L-7 that no window flashes on `schtasks /Run` and switch to `-H windowsgui` if it does.
- **Reproducibility.** `-trimpath`, `-buildvcs=false`, pinned toolchain and a committed `go.sum` make the binary reproducible across machines; the SHA-256 the Lychee build embeds for the Windows copy step (section 4) is computed from the artifact at package time, not from source.

  ```yaml
      - Contents/Resources/helper/lychee-netd   # so osx-sign signs it (hardened runtime, notarization)
  afterPack: scripts/after-pack.mjs             # runs check-torrent-package.mjs, then check-netd-package.mjs
  ```

  `${os}` expands to `mac`/`win`/`linux` and `${arch}` to `x64`/`arm64`, which is why `build-netd.mjs` names its directories that way. The exact path form `mac.binaries` expects is an appendix check item.
- **`scripts/check-netd-package.mjs`** (afterPack, like `check-torrent-package.mjs`): asserts that `resources/helper/` holds a `lychee-netd[.exe]` whose header matches the package's OS and architecture (ELF `e_machine`, Mach-O `cputype`, PE `Machine`), that `go version -m` on it reports the expected `main.version` and `CGO_ENABLED=0`, that on `win-x64` `wintun.dll` and `wintun-LICENSE.txt` sit next to it with the pinned SHA-256, that on `win-arm64` there is no binary (only `UNSUPPORTED`), and that `THIRD-PARTY-NOTICES-netd.md` and `licenses/net-merge-LICENSE.txt` are present. A build that fails any of these does not produce an installer.
- **`scripts/fetch-wintun.mjs`.** Downloads `https://www.wintun.net/builds/wintun-0.14.1.zip`, verifies the zip's SHA-256 `07c256185d6ee3652e09fa55c0b673e2624b565e02c4b9091c79ca7d2f24ef51` (the value net-merge's `fetch-wintun.ps1` pins) and the extracted `bin/amd64/wintun.dll`'s own pinned SHA-256, copies `wintun.dll` and `LICENSE.txt` (as `wintun-LICENSE.txt`) into `build/netd/win-x64/`, asserts the license text equals the reference copy kept in the repo at `build/licenses/wintun-LICENSE.txt` (from S1's PR #11), and on Windows builders additionally runs `Get-AuthenticodeSignature` through `powershell.exe` and requires `Status = Valid` with a WireGuard LLC subject. The DLL is never committed.
- **Signing.** macOS: `mac.binaries` above; the Go binary needs no entitlements beyond `entitlementsInherit`. Windows: when a certificate is configured, verify electron-builder signs `resources/helper/lychee-netd.exe` (appendix); `wintun.dll` keeps WireGuard LLC's signature and is never re-signed.
- **Linux packages.** electron-builder's `deb.afterInstall` and `rpm.afterInstall` (both pointing at `build/linux/after-install.sh`): the packaged copy sits under `/opt/Lychee/resources/helper/`; the script installs a root-owned `0755` copy at `/usr/lib/lychee/lychee-netd` (the fixed path the client and the spec use) and runs `setcap cap_net_admin,cap_net_raw+ep` on it, on every install and upgrade because replacing the file drops its capabilities. `deb.afterRemove`/`rpm.afterRemove` delete it. AppImage: nothing; Lychee uses `pkexec` (section 4).

## 14. Decisions and open questions

Decided (Andrew):

1. **Lifecycle.** The helper keeps running while Lychee is in the tray and stops when Lychee quits; on its own it exits 10 s after the client disconnects without a `quit` (spec section 10.3), so nothing survives a crash of Lychee.
2. **macOS privilege path.** One-time sudoers install with the exact rule of section 4 (no wildcards), root-owned helper copy in `/Library/PrivilegedHelperTools`, one admin prompt at setup and one per helper update; `SMAppService` once Developer ID signing lands.
3. **In-repo port, no fork, no upstream PRs.** `native/netd` is Lychee code; `UPSTREAM.md` records the base commit; net-merge is credited in `NOTICE` and the About popover.
4. **Defaults.** Merging off until opted in; autopause on; IPv6 `auto`.
5. **Windows arm64 deferred.** The arm64 Windows build ships without netd and shows "Unsupported here"; amd64 only for now.

## Security requirements (from review)

- macOS: the sudoers rule names only the exact helper path `/Library/PrivilegedHelperTools/gg.tame.lychee.netd` with the exact argument vector `serve --control /var/run/lychee-netd/netd.sock`; no wildcards, no trailing `*`, no `""` empty-argument variant, no `SETENV`. The file `/etc/sudoers.d/lychee-netd` is `0440`, `root:wheel`, validated with `visudo -cf` before `rename`, read back and byte-compared by the elevated setup step, and checked with `sudo -n -l` for the exact command line before every launch. The launch is exactly `sudo -n /Library/PrivilegedHelperTools/gg.tame.lychee.netd serve --control /var/run/lychee-netd/netd.sock`. The helper binary and every parent directory must be root-owned and not user-writable; Lychee verifies this before enabling merging and the helper's own self-check refuses otherwise.
- Helper control channel is a Unix domain socket (macOS `/var/run/lychee-netd/netd.sock`, Linux `$XDG_RUNTIME_DIR/lychee/netd.sock` or `/run/lychee-netd/netd.sock`) or a named pipe (Windows `\\.\pipe\lychee-netd-<SID>`) restricted to the logged-in user, with peer credential checks and a strict command allowlist. No localhost TCP port.
- Windows: the elevated task never runs a helper from the per-user `%LOCALAPPDATA%` install. One UAC prompt copies `lychee-netd.exe` and the unmodified `wintun.dll` (plus its license) to `%ProgramFiles%\Lychee\helper`; Lychee verifies only SYSTEM/Administrators can write there (refuses otherwise) and verifies the helper's Authenticode signature or its SHA-256 against the hash embedded in the Lychee build. The scheduled task points only at that path, and updates go through the same elevated copy with version and hash checks. `wintun.dll` stays unmodified and is used only through `wintun.h`, per its license.
- Windows named pipe: DACL for the logged-in user's SID plus SYSTEM only (SDDL `O:<SID>D:P(A;;GRGW;;;<SID>)(A;;GA;;;SY)`, no Administrators ACE), `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE` against squatting, per-connection checks via `GetNamedPipeClientProcessId` and the client token's user SID; the client verifies the server's SID before writing.
- Windows administrator account (S2): on a standard account the UAC credential prompt elevates as another administrator, so the helper belongs to that administrator and Lychee cannot connect. This fails safe (no other user can control the helper, the client cannot connect, nothing is captured because merging is off by default), but Lychee MUST detect it before launching (`CheckTokenMembership` against Administrators on the linked token) and after launching (exit 6, or a running helper whose pipe cannot be opened or whose token SID differs from the client's) and show "Combining connections system-wide needs an administrator account on this PC", never "helper unavailable". `lychee-netd serve` checks that its own token is elevated and in Administrators before doing anything and exits 6 (`needs_admin`) otherwise, because a `RunLevel HighestAvailable` task gives a standard user a limited token.
- Linux AppImage: the `pkexec` path runs a binary from a user-writable folder; accepted because pkexec requires the admin password on every start. deb/rpm install the helper root-owned at `/usr/lib/lychee/lychee-netd` and re-apply `setcap` on every upgrade.
- Single instance: `lychee-netd` holds its own lock names and refuses to start (exit 4, "another connection-merging tool is running") when a standalone net-merge holds its lock, because both would install the same `/1` routes.
- Build integrity: the helper is built from this repository with a pinned Go toolchain, `CGO_ENABLED=0` and `-trimpath`; the afterPack check refuses a package whose helper has the wrong architecture, version or build settings; `wintun.dll` is fetched with a pinned hash and signature check and never committed.
- The test that pins Lychee's own connections to their adapter while merging is active lands early in the stack (L-4).
